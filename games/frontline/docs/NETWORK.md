# 네트워크 안정성 (측정과 개선)

> 엔진 구조는 [ENGINE.md](ENGINE.md), 메시지는 [PROTOCOL.md](PROTOCOL.md). 이 문서는 "원격 플레이어가 순간이동한다"는 문제를 **측정으로 원인 분리**하고 고친 기록과, 다시 재는 방법이다.

## 결론
원인은 서로 독립된 두 가지였고, 둘 다 패킷 손실·지연 변동이 있는 연결에서만 나타났다.

| # | 원인 | 위치 | 근거 (손실 3%, RTT 150ms, 4명) |
|---|---|---|---|
| ① | 손실로 메시지가 0.3초씩 정체되면 **고정 100ms 보간 버퍼가 바닥나** 원격 플레이어가 멈췄다 튄다. (설계에 있던 "3tick 예측"도 `sample` 의 조건 오류로 한 번도 실행되지 않았다) | 클라이언트 | 받는 쪽만 손실: 튐 68 · 멈춤 77(최대 273ms) |
| ② | **서버가 입력을 몰아서 처리**한다. 보내는 쪽 입력이 늦게 몰려 오면 한 tick 에 전부 계산 → 서버 위치 자체가 순간이동(관찰자는 막을 수 없다) | 서버 | 보내는 쪽만 손실: 서버 위치 튐 59회 (최대 70m/s) |
| ③ | Oracle `VM.Standard.E2.1.Micro`(CPU 1/8 OCPU 기준)가 **30~60ms 씩 CPU 를 못 받아** 멈춘다. ②를 더 자주 일으킨다 | 호스트 | 게임 코드 없는 시험에서도 재현 (아래) |

서버 사양이 모자란 것은 아니다: 평균 tick 0.4~0.6ms(예산 16.7ms), CPU 5~10%. 문제는 평균이 아니라 **가끔 생기는 정지**와 그것이 입력 폭주로 이어지는 구조였다.

## 변경 사항
| 파일 | 변경 |
|---|---|
| `server/game/room.js` | **입력 큐**: 받은 cmd 를 쌓아 두고 tick 마다 1개(3개 넘게 밀리면 2개) 처리. 몰려 와도 남에게는 최대 2배속으로 보일 뿐 순간이동하지 않는다. 시간 예산(속도 핵 방지)은 그대로, 큐가 0.6초 넘게 밀리면 오래된 것부터 버림. `INPUT_QUEUE=off` 로 예전 방식 |
| `client/js/interp.js` (신규) | **적응형 서버 시계(NetClock)**: 보간 버퍼를 수신 지연 편차(최근 4초 95%)에 맞춰 6~14tick 으로 늘리고 줄임. 재생 위치는 거꾸로 가지도 점프하지도 않는다(속도 90~125%). 데이터가 끊기면 최신 스냅샷+3tick 에서 멈췄다가 다시 오면 부드럽게 따라잡는다. `sample` 의 예측 조건 수정 |
| `client/js/netdiag.js`, `main.js`, `net.js`, `remotes.js`, `predict.js` | **F3 진단**: RTT·수신 간격/지터/최대 간격·메시지 수/KB·보간 버퍼·예측 비율·원격 튐·내 위치 보정·FPS. 1초마다 `ping`/`pong` |
| `server/perf.js` (신규) | 서버 계측: tick 시간, tick 간격, 브로드캐스트 시간, 이벤트 루프 지연, GC, 길찾기, CPU, 메모리, 메시지 수/KB. `/perf` · `/status` · `PERF_LOG=1` |
| `shared/sim/config.js` | `MAX_REWIND_TICKS` 18→22 (버퍼가 늘어도 명중 되감기가 맞도록) |
| `tools/netsim/` | 장애 재현 프록시 + 측정 도구 (아래) |

유지한 것: 서버 권한 60Hz, 30Hz 스냅샷, WebSocket/JSON 프로토콜, 클라이언트 예측·보정, 랙 보정. 메시지 형식은 `ping`/`pong` 추가 외 변경 없음.

## 개선 전후 (같은 도구·같은 조건, 4명, 25초)
| 환경 | 보간 튐 (전→후) | 멈춤 (전→후) | 서버 위치 튐 (전→후) | 위치 오차 p99 (전→후) | 버퍼 평균 (전→후) |
|---|---|---|---|---|---|
| 양호 30ms | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 | 100 → 100ms |
| 보통 80ms | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 | 100 → 100ms |
| 지연 150ms | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 | 100 → 108ms |
| 지터 100±40ms | 0 → 0 | 0 → 0 | 8 → 0 | 15 → 4cm | 100 → 125ms |
| 불안정 100ms 1% | 4 → 0 | 4 → 0 | 22 → 0 | 28 → 4cm | 100 → 126ms |
| 매우 불안정 150ms 3% | 45 → 1 | 58 → 0 (최대 201ms) | 50 → 0 | 142 → 18cm | 100 → 230ms |

10명 (중간 버전으로 측정): 3% 손실에서 튐 168→0, 멈춤 164→0, 서버 위치 튐 109→0. 서버 tick 0.6~0.8ms, CPU 8~10%(봇 부하 포함).
**대가**: 손실이 심하면 지연(버퍼)이 늘어난다. 양호한 연결에서는 그대로 100ms.

## Oracle 서버 검증 (2026-11-19, `VM.Standard.E2.1.Micro`, 오사카)
- 사양: 2 vCPU(AMD EPYC 7551, 1/8 OCPU 기준), 메모리 약 500MB + 스왑 3GB, 3000/tcp 만 개방, 서비스 재시작 0회.
- **CPU 제한 확인**: 코어 1개를 100% 쓰면 steal 약 25%(총 CPU 기준). 게임 코드 없이 "16.7ms 마다 N ms 계산":
  3% 부하 → tick 간격 25ms 초과 3회/분(최대 66ms), 12% → 계산 중 정지 49.6ms, 36% → 정지 25ms 초과 48회/분(최대 62.8ms). 부하가 없는 빈 프로세스는 정지 없음.
- 운영 조건(사람 1 + AI 봇): tick 평균 0.5ms, 그러나 tick 간격 최대 47~57ms, 늦은 tick 8~18회/분. **길찾기는 원인이 아님**(803회 중 최대 3.9~29.6ms, 같은 크기의 정지가 아무 작업에나 끼어듦).
- 10명 봇 부하(네트워크 지연 0): 입력 큐 끔 → 서버 위치 튐 **14회(최대 49m/s)**, 켬 → **0회(최대 15m/s)**. 호스트 정지(tick 간격 최대 82~88ms)는 그대로지만 순간이동으로 이어지지 않는다.
- **이 PC → Oracle 경로**: 30초간 서버 TCP 재전송 35/534 조각(6.5%), RTT 중앙 184ms · p90 659ms · p99 1.2초. 같은 PC 에서 Cloudflare 대조군에도 1.1초 지연이 있어 손실의 일부는 이 PC 의 네트워크일 수 있다(Wi-Fi 5GHz, -55dBm 양호, 기업망 WPA2-Enterprise). 이 정도 손실은 위 "매우 불안정" 시험보다 가혹하다.

## 해결하지 못한 것 · 다음 단계
1. **TCP 의 한계**: WebSocket 은 손실 시 뒤따르는 메시지까지 막힌다(head-of-line blocking). 버퍼로 가리는 것이 한계이고, 근본 해결은 위치 스냅샷을 **WebRTC DataChannel(비신뢰·비순서)** 로 보내는 것.
2. **Oracle 인스턴스**: Micro 의 CPU 제한은 코드로 없앨 수 없다. 인스턴스를 키우거나(E2.1 이상 · Always Free 의 Ampere A1 은 ARM 이며 가용성 확인 필요) 같은 리전에서 더 가까운 곳(한국 리전)으로 옮기는 것을 검토. 이 변경은 미확인이라 하지 않았다.
3. 서버 정지 자체는 남아 있다(입력 큐가 가릴 뿐). 정지가 잦아지면 `MAX_QUEUE`·`CATCHUP_AT` 를 조정.
4. 메시지가 많다(클라이언트당 약 60~80msg/s, 40KB/s): `snap`·`me`·`ev` 를 한 메시지로 묶으면 줄일 수 있으나 지금은 병목이 아니라 하지 않았다.
5. 3% 손실에서도 보간 튐 1회/25초가 남는다(버퍼 상한 14tick 으로 지연과 맞바꾼 값).

## 다시 재는 방법
```bash
npm run netsim -- --impl new --suite --players 4 --secs 25     # 6개 프로필 (양호·보통·지연·지터·1%·3%)
npm run netsim -- --impl new --players 10 --rtt 150 --jitter 30 --loss 0.03 --impair observer   # 받는 쪽만 / movers = 보내는 쪽만
npm run netsim -- --impl legacy --queue off ...                # 개선 전 동작 (tools/netsim/legacy.mjs, INPUT_QUEUE=off)
NETSIM_STALL=45:4000 npm run netsim -- ...                      # 서버가 평균 4초마다 45ms 멈추는 상황 (Oracle 재현)
node tools/netsim/prodload.mjs --humans 1 --secs 60 --mode dom # 운영과 같은 조건의 서버 부하 (사람 + AI 봇)
node tests/net.test.mjs · node tests/netbrowser.test.mjs        # 단위 · 실제 Chrome(프록시 경유)
```
브라우저에서는 **F3**. 서버는 `/perf`(최근 2분, 1초 단위), `PERF_LOG=1`. 프록시(`tools/netsim/proxy.mjs`)는 TCP 수준에서 지연·지터·손실을 흉내 낸다(손실 = 재전송 대기 + 뒤따르는 메시지 정체). 실제 장비의 큐 지연·대역폭 제한은 흉내 내지 않으며, 리눅스에서는 `tc netem` 으로 같은 시험을 할 수 있다.
